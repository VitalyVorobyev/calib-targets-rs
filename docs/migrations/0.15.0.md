# Migrating to 0.15.0

**Breaking, and confined to the marker-board detector, its printable model, and
the bindings that mirror them.** If you do not use `calib-targets-marker` or
`MarkerBoardTargetSpec`, nothing here applies and the upgrade is a version bump.

This is a minor rather than a patch for one reason: fields were *removed* from
public structs. `#[non_exhaustive]` stops a downstream crate constructing or
exhaustively destructuring them, but it never stopped reading a field, and
`#[serde(deny_unknown_fields)]` means a stored JSON config naming a removed
field now fails to deserialize rather than being ignored.

## Why the marker board changed

A board rendered with `inner_square_rel` above ~0.3 could come back with the
frame 90 or 180 degrees rotated while the detector reported three clean circle
matches and no error ([#96]). Every corner then carried a wrong `(i, j)` label.
Two things had to be fixed — the circle scorer had no test that a candidate was
actually *round*, so the white inset drawn inside every black square scored as a
marker disk; and frame resolution ranked hypotheses by contrast rather than by
agreement, so two bright false candidates could outvote three real ones. The
[CHANGELOG](../../CHANGELOG.md) has the full account.

## The printed disk diameter moved

`CircleScoreParams::diameter_frac` is **removed**. It stated the same physical
quantity as the printable spec's `circle_diameter_rel`, and the two could
disagree: a board printed at `0.45` was probed at the default `0.5`, putting
every radius the scorer uses 11% off. The board now says it once.

```rust,ignore
// Before
let params = MarkerBoardParams::for_board(board);
params.circle_score.diameter_frac = 0.45;
```

```rust,ignore
// After — on the board, which is what it describes.
let board = board.with_circle_diameter_rel(0.45);
let params = MarkerBoardParams::for_board(board);
```

In JSON (Python, WASM, stored configs), move `circle_score.diameter_frac` to
`board.circle_diameter_rel`. Leaving it in place is a deserialization error, not
a silent ignore. In C, `ct_circle_score_params_t` loses `diameter_frac` and
`ct_marker_board_layout_t` gains `circle_diameter_rel`.

## Circle matching is a frame sweep, so its distance knob is gone

`CircleMatchParams::max_distance_cells` and `CircleMatch::distance_cells` are
**removed**, and `CircleMatch::with_match` drops its `distance_cells` argument.

Both encoded the same defunct idea: matching a circle by the distance between a
*board* cell index and a *detected* cell index, which presumes the translation
the alignment is supposed to establish. Resolution now enumerates every
`(rotation, translation)` and verifies it, so a match is an exact integer
coincidence and a distance could only ever have reported zero. Delete the field;
there is nothing to replace it with.

## `min_offset_inliers` defaults to 3

Was `1`. The three circles exist for exactly one reason — to break the board's
4-fold rotational symmetry — and fewer than all three cannot do it: any single
circle is consistent with all four rotations, and two leave no redundancy to
check a wrong pairing against.

This costs nothing on a board where all three markers are visible. It costs
recall on one where a marker is occluded or blown out, which used to return a
frame that was unverified rather than correct. If you need the old behaviour,
set it explicitly and understand that you are trading the "never a wrong label"
half of the detection contract for recall:

```rust,ignore
params.match_params.min_offset_inliers = 2;
```

## A new failure, and a new rejection

- `MarkerBoardDetectError::AlignmentAmbiguous { inliers, runner_up }` — two
  board frames explain the detected circles equally well, so neither is
  returned. The enum is `#[non_exhaustive]`; code with a wildcard arm compiles
  unchanged and now sees a case it previously received as a confidently wrong
  answer.
- `PrintableTargetError::InvisibleCircle { i, j }` — a marker circle whose
  polarity matches the square underneath. The checkerboard's colour phase is
  fixed (square `(0, 0)` is black), so a white disk is only visible on an even
  `i + j` and a black one only on an odd one; anything else rendered nothing at
  all. A spec that previously "worked" this way was producing a board with
  fewer markers than it claimed.

## Corrected without action on your part

- **`MarkerBoardTargetSpec::default_circles` returned three invisible circles**
  on any board whose centre cell has odd parity — a 6x8 board among them, where
  it emitted the exact polarity inverse of every shipped fixture. It now anchors
  the L on an even-parity cell. `MarkerBoardSpec::default()` on the detector
  side carried the same contradiction and now matches. If you passed either
  through unchanged, your board starts working.
- **The inner-square inset is no longer painted under a marker circle.** It is
  drawn in the same white a disk needs, so it merged with one and — once
  `inner_square_rel` reached `circle_diameter_rel` — swallowed it. Regenerate
  any printed board that carries both.
- **A fully detected board no longer drops the id and `target_position` of its
  last row and column** (13 of 48 corners on a 6x8). A circle layout names
  *squares*, so the resolved frame labelled corners `1..=cols` — outside the
  board's own index range, with a labelled bounding-box minimum of `(1, 1)`
  rather than `(0, 0)`. Labels are inner-corner indices now, and
  `target_position` measures from the board's outer corner, matching the
  printable spec's `resolved_points`. **If you stored marker-board corner ids or
  target positions from an earlier release, they are shifted by one cell** in
  both axes relative to what 0.15.0 produces.

## Diagnostics gained fields

`CircleCandidate::squareness` (what the new shape gate measured: `0` for a
disk, `0.48..0.62` for a square inset), and `MarkerBoardDiagnostics` gains
`alignment_runner_up_inliers` and `alignment_ambiguous`. Additive on an opt-in
surface with a documented looser stability promise.

## C ABI 4.0.0 -> 5.0.0

Three struct-layout-breaking changes: `ct_marker_board_layout_t` gains
`circle_diameter_rel`, `ct_circle_score_params_t` loses `diameter_frac`, and
`ct_circle_match_params_t` loses `max_distance_cells`. **Relink, do not just
recompile** — a consumer built against 4.0.0 passes structs of the wrong size.
