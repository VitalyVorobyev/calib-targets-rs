# Migrating to 0.14.0

Additive on every published surface. No type is removed or renamed, the C ABI
stays at **4.0.0**, and detection results are unchanged for every board printed
with the default one-cell marker border — which is every board the previous
releases could describe.

There is exactly one behaviour change, below.

## `scan.border_bits` is derived from the board

`CharucoBoardSpec` now carries `border_bits`, the width in marker cells of the
black ring printed around each marker payload (OpenCV's `borderBits`). It is a
physical property of the printed target, so the board spec is where it lives,
and `CharucoDetector::new` now **overwrites `params.scan.border_bits` with the
board's value on every construction path**.

If you were reaching past the board spec to describe a wide-ring board:

```rust,ignore
// Before — the only way to say "this board has a two-cell ring".
let mut params = CharucoParams::for_board(spec);
params.scan.border_bits = 2;
```

```rust,ignore
// After — say it on the board, which is what it describes.
let spec = spec.with_border_bits(2);
let params = CharucoParams::for_board(spec);
```

The old form now silently resolves back to the board's value (`1` unless you
set it), so it must be migrated rather than left in place.

Why unconditionally, rather than repairing an "unset" scan value: the scan
default *is* `1`, which is indistinguishable from a caller who meant 1. A
conditional repair would therefore leave `CharucoParams::for_board` as the only
construction path whose scan config agreed with its own board — reassigning
`params.board`, or deserialising a config that names the board and omits `scan`
(the shape the Python bindings and any stored JSON config take), would keep
sampling the ring of whatever board the params were seeded from.

Two fields describing one physical fact is the actual defect; deriving one from
the other removes it.

### What this does *not* mean

The previous behaviour was not a decode failure. Measured on a synthetic
render, the board-level matcher aligns a `border_bits = 2` — even `= 3` — board
correctly while sampling it with a one-cell ring, because the inset sampling
grid lands inside the payload either way. What was genuinely wrong is everything
computed *from* the ring: the `min_border_score` gate scored cells that are not
the printed border, and diagnostics reported a ring the board does not have. The
tolerance is a coincidence of one inset value and should not be relied on.

## New, no action required

- **`CharucoBoardSpec::border_bits` / `with_border_bits`**, mirrored on the
  printable `CharucoTargetSpec` and the Python `CharucoBoardSpec`. Defaults to
  1; `border_bits = 0` is now rejected with `CharucoBoardError::InvalidBorderBits`
  (a marker with no ring cannot be told from the white square under it).
- **`render_target_bundle_json(doc)` on the WASM surface** takes a full
  `PrintableTargetDocument` — page size, orientation, margin, and every spec
  field the fixed-arity `render_*_bundle` helpers do not name. Those helpers are
  unchanged; handing the new function the page one of them would have
  synthesised returns a byte-identical SVG.
- **`PrintableMarkerCircleSpec`** in the WASM TypeScript declarations. The
  printable model's circle (`{ i, j, polarity }`) needs a name distinct from the
  detector's `MarkerCircleSpec` (`{ cell, polarity }`): two Rust crates may
  share a type name, one `.d.ts` module may not.
