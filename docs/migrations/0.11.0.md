# Migration Guide — 0.11.0

This guide collects every breaking change in the 0.11.0 release for
upstream consumers of the `calib-targets` workspace, with before/after
snippets for Rust, the JSON config wire format, the Python bindings, the
C ABI, and the WASM / TypeScript surface.

0.11.0 is dominated by one upstream event — **`chess-corners` 1.0**, an API
freeze that removed or reshaped most of the corner front-end's public
surface — plus a batch of workspace-side consolidations that had been
queued behind it.

The changes fall into seventeen themes:

1. [`chess-corners` 1.0: the ChESS threshold is a plain `f32`](#1-the-chess-threshold-is-a-plain-f32)
2. [`nms_radius` / `min_cluster_size` moved to a `detection` block](#2-nms_radius--min_cluster_size-moved-to-a-detection-block)
3. [`DescriptorRing` is removed](#3-descriptorring-is-removed)
4. [`contrast` / `fit_rms` are gone — and so is the fit-RMS pre-filter](#4-contrast--fit_rms-are-gone--and-so-is-the-fit-rms-pre-filter)
5. [`chess_corners::low_level` moved to the `chess-corners-core` crate](#5-chess_cornerslow_level-moved-to-chess-corners-core)
6. [`nalgebra` 0.34 → 0.35](#6-nalgebra-034--035)
7. [`GridCoords` is replaced by `Coord { u, v }`](#7-gridcoords-is-replaced-by-coord--u-v-)
8. [The seed-and-grow grid builder is retired](#8-the-seed-and-grow-grid-builder-is-retired)

If you only read corners off a detection result and never construct config
structs by literal, themes 1–6 do not affect you at runtime — but theme 7
changes the JSON key names of every grid label, so report parsers do need a
look.

**Detection behaviour.** The ChESS response kernel is unchanged between
`chess-corners` 0.11.2 and 1.0.0, so themes 1–3, 5, and 6 are pure API
reshaping with byte-identical output. Theme 4 is the one deliberate
behavioural change in this release, and it is discussed on its own terms
below.

## 1. The ChESS threshold is a plain `f32`

`chess_corners::Threshold` — the tagged enum with `Absolute` and `Relative`
variants — is removed. The ChESS strategy now reads a single `f32` as an
absolute floor on the raw response.

**There is no ChESS relative mode any more.** Relative thresholding survives
only on the Radon strategy, where it means "a fraction of the per-frame
maximum". If you were passing `Threshold::Relative(_)` to a ChESS config,
there is no mechanical translation; pick an absolute floor instead. The
workspace default, `15.0`, is a reasonable starting point for 8-bit imagery
and is what `calib_targets::detect::default_chess_config()` uses.

### Rust

```rust
// before
let cfg = DetectorConfig::chess().with_threshold(Threshold::Absolute(15.0));
let low = DetectorConfig::chess().with_threshold(Threshold::Relative(0.05));

// after
let cfg = DetectorConfig::chess().with_threshold(15.0);
let low = DetectorConfig::chess().with_threshold(8.0); // pick an absolute floor
```

### JSON config wire format

```jsonc
// before
{ "threshold": { "absolute": 15.0 } }

// after
{ "threshold": 15.0 }
```

### If you drive `ChessParams` directly

The low-level `ChessParams` had a `threshold_rel` / `threshold_abs` pair.
These collapse into one `threshold` field.

> **Note — your `threshold_rel` was probably already a no-op.** Pre-1.0,
> `chess-corners-core` resolved the floor as
> `threshold_abs.unwrap_or(threshold_rel * max_response)`, and
> `ChessParams::default()` set `threshold_abs: Some(0.0)`. So code that
> defaulted a `ChessParams` and then set only `threshold_rel` was running at
> an absolute floor of `0.0`, not at the relative value it appeared to
> request. Mapping such code to `threshold = 0.0` is exactly
> behaviour-preserving; "preserving" the relative number would be a silent
> behaviour *change*. Two call sites inside this workspace were in precisely
> that state.

### Upstream default moved

`chess-corners` 1.0 changed its own `DetectorConfig::chess()` default from
`0.0` to `30.0`. The workspace has always overridden it and continues to use
`15.0`, so `default_chess_config()` produces exactly the corner set it did
under 0.11. If you build a bare `DetectorConfig::chess()` yourself, you are
now starting from `30.0`.

## 2. `nms_radius` / `min_cluster_size` moved to a `detection` block

Both fields left the ChESS strategy config and became strategy-independent
detection parameters.

### Rust

```rust
// before
let cfg = DetectorConfig::chess().with_chess(|c| {
    c.nms_radius = 3;
    c.min_cluster_size = 2;
});

// after
let cfg = DetectorConfig::chess().with_detection(|d| {
    d.nms_radius = 3;
    d.min_cluster_size = 2;
});
```

### JSON config wire format

```jsonc
// before
{
  "strategy": { "chess": { "nms_radius": 2, "min_cluster_size": 2, "ring": "canonical" } }
}

// after
{
  "strategy": { "chess": { "ring": "canonical" } },
  "detection": { "nms_radius": 2, "min_cluster_size": 2 }
}
```

The Python bindings reject the old key locations with an explicit error
rather than silently defaulting — see [Python](#python).

The *low-level* `ChessParams` keeps both fields; only the facade
`ChessConfig` lost them.

## 3. `DescriptorRing` is removed

The descriptor ring radius is no longer independently selectable — the
descriptor always follows the detector's ring radius, which is what the
previous default (`DescriptorRing::FollowDetector`) already did. Delete the
setting; at the default there is no behaviour change.

```rust
// before
let cfg = DetectorConfig::chess().with_chess(|c| {
    c.descriptor_ring = DescriptorRing::FollowDetector;
});

// after
let cfg = DetectorConfig::chess();
```

The `descriptor_ring` JSON key and the C `descriptor_use_radius10` field are
removed likewise.

## 4. `contrast` / `fit_rms` are gone — and so is the fit-RMS pre-filter

`chess-corners` 1.0 no longer reports `contrast` (local light/dark
separation) or `fit_rms` (corner-model fit residual) on a corner. A corner
now carries a sub-pixel position, two undirected axes each with a 1σ angular
uncertainty, and a `strength` response magnitude.

Consequently:

- **`calib_targets_chessboard::ChessCorner` loses `contrast` and `fit_rms`.**
  Construct it with `position`, `axes`, `strength`.
- **`ChessboardAdvancedTuning::max_fit_rms_ratio` is removed** (it was the ratio `k` in
  `fit_rms ≤ k · contrast`, default `0.5`). Delete it from Rust literals,
  JSON configs, Python `ChessboardParams`, and the C
  `ct_chessboard_advanced_t` struct.
- **`CornerDescriptor::axes` is now `Option<[AxisEstimate; 2]>`.** The
  workspace always fits orientation, so `None` maps to the existing
  no-information sentinel (`AxisEstimate::default()`, `sigma = π`).

### The replacement admission gate

The chessboard pipeline's Stage 1 pre-filter used to admit a corner's axes
when `strength ≥ min_corner_strength` **and**
`fit_rms ≤ max_fit_rms_ratio · contrast`. The second half is no longer
expressible. It is replaced by a gate on the axes' own reported uncertainty:

```text
strength ≥ min_corner_strength   AND   max(σ₀, σ₁) ≤ axis_align_tol_rad
```

`axis_align_tol_rad` (default 15°) is the tolerance the topological builder's
cell test *already* applies to those same axes. The gate is therefore
**derived, not a new constant**: an axis estimate whose own 1σ spread is
wider than the alignment window cannot answer the question the cell test
poses of it, so admitting it adds noise to edge classification rather than
evidence. Loosening the cell test loosens admission by exactly the same
amount, and there is no separate knob to tune — which is why nothing replaced
`max_fit_rms_ratio` in `ChessboardAdvancedTuning`.

> The topological builder also carries a `max_axis_sigma_rad` (0.6 rad). That
> is a much looser internal backstop, not an admission gate, and it is
> unrelated to this change.

**Behavioural note.** This is the one place in 0.11.0 where detection output
moves. Across the workspace regression corpus the change is recall-positive
in aggregate, and — the property that actually matters — **no frame gained a
wrong `(i, j)` label**; the wrong-label, over-long-edge, and duplicate-pixel
counters are unchanged. Dense, high-corner-count frames are where the two
criteria disagree most: some lose a small fraction of labelled corners
relative to the fit-RMS rule. If you pinned a minimum-corner expectation
against a very dense board, re-measure it.

## 5. `chess_corners::low_level` moved to `chess-corners-core`

The `low_level` and `unstable` modules are removed from the `chess-corners`
facade. The contract they exposed now lives at the root of the
`chess-corners-core` crate, which you must depend on directly.

```toml
# Cargo.toml
chess-corners = "1.0"
chess-corners-core = "1.0"   # only if you drive the response/detect stages by hand
```

```rust
// before
use chess_corners::low_level::{ChessParams, RefinerKind, ImageView, Roi};

// after
use chess_corners_core::{ChessParams, RefinerKind, ImageView, Roi};
```

`chess_response_u8_patch`, `detect_corners_from_response_with_refiner`, and
`Refiner` move the same way.

**`PyramidParams` is not re-exported by 1.0** — it moved to
`box-image-pyramid`. Construct
`MultiscaleConfig::Pyramid { levels, min_size, refinement_radius }` directly
instead of routing through a `PyramidParams` intermediate.

Refiner configs are `#[non_exhaustive]` upstream now, so struct literals no
longer compile; use `default()` plus field assignment.

## 6. `nalgebra` 0.34 → 0.35

`nalgebra` types appear in the public API of `projective-grid` and
`calib-targets-core` (`Point2<f32>`, `Matrix3<f32>`,
`LabeledCorner.position`, …), so consumers must move to the same major
version to interoperate. No workspace source change was required and
detection output is byte-identical.

The bump also drops the unmaintained `paste` crate from the `nalgebra` →
`simba` path (see the CHANGELOG *Security* section).

## 7. `GridCoords` is replaced by `Coord { u, v }`

The workspace-local `GridCoords { i, j }` type is deleted with no deprecated
alias; `projective_grid::Coord { u, v }` is the single canonical
grid-coordinate type, re-exported from `calib-targets-core` and the facade.

**The axis convention is preserved exactly**: the old `i` (grid-right, first
axis) is `Coord::u`, and the old `j` (grid-down, second axis) is `Coord::v`.

Affected output fields: `LabeledCorner.grid`, `ChessboardCorner.grid`,
`CharucoCorner.grid`, `MarkerBoardCorner.grid`, `PuzzleBoardCorner.grid`,
`MarkerDetection.gc`, `ResolvedTargetPoint.grid`.

### Report JSON

```jsonc
// before
{ "grid": { "i": 3, "j": 5 } }

// after
{ "grid": { "u": 3, "v": 5 } }
```

The marker-board *cell* index (`MarkerCircleSpec.cell`, Rust `CellCoords`) is
**unaffected** and keeps its `{ "i", "j" }` shape.

**The C ABI is unchanged here.** `ct_grid_coords_t` keeps its historical
`{ i, j }` C field names and struct layout; the Rust→C conversion maps
`Coord::u → i` and `Coord::v → j`.

## 8. The seed-and-grow grid builder is retired

`Topological` is the sole grid builder. Both seed-and-grow engines — the
chessboard pipeline's own and `projective-grid`'s
`SquareAlgorithm::SeedAndGrow` — are deleted, and ChArUco, PuzzleBoard, and
marker boards all run the topological builder now.

- `GraphBuildAlgorithm` and `SquareAlgorithm` collapse to single-variant
  `#[non_exhaustive]` enums (only `Topological`), retained as reserved config
  seams.
- **The wire string `"seed_and_grow"` no longer deserializes.** Remove it
  from stored configs.
- The `ChessboardAdvancedTuning` block drops its seed-and-grow-only stage
  knobs: `seed_*`, `rescue_*`, `refit_*`, `boundary_extension_*`,
  `partial_slot_flip_*`, and the dead BFS-validate tolerances. The removal is
  propagated through the FFI / Python / WASM / Studio surfaces.
- The chessboard rich `DebugFrame` diagnostics and the experimental
  `OrientationSource::NeighbourEdges` path are removed with the engine.

A `min_corner_strength` floor now pre-filters the marker-bit corners that the
old ChArUco engine pin had guarded against.

## 9. Smaller surface removals

- **`calib_targets_chessboard::ChessboardDetector::new` is now fallible**
  (`-> Result<Self, ChessboardParamsError>`), validating the configuration up
  front. The previous infallible `new` + `try_new` pair is gone — rename your
  `try_new` calls to `new`. `MarkerBoardDetector::new` is likewise fallible,
  and `PuzzleBoardSpecError` gains a `Chessboard` variant so
  `PuzzleBoardDetector::new` surfaces an invalid embedded chessboard config.

- **The legacy ChArUco vote matcher is retired.** The board-level matcher was
  already the default, so detection behaviour is unchanged.
  `CharucoParams::use_board_level_matcher` and `CharucoParams::max_hamming`
  are removed. Since `CharucoParams` now uses `deny_unknown_fields` (see the
  enforcement in theme 17), a config that still carries either key is
  **rejected** on deserialization — drop them.
  `MatcherDiagKind` and `ComponentDiagnostics.matcher` are removed, so the
  `matcher` key is dropped from the ChArUco diagnostics JSON.

- **ChArUco and PuzzleBoard diagnostics are behind an opt-in `diagnostics`
  cargo feature** (default off), matching `calib-targets-chessboard`. The
  `diagnostics` module, its type re-exports, and `detect_with_diagnostics`
  reach the public surface only with the feature enabled; the facade
  `calib-targets/diagnostics` feature forwards to all three detector crates.

  ```toml
  # Cargo.toml — turn the surface back on
  calib-targets = { version = "0.11", features = ["diagnostics"] }
  ```

- **`ChessboardParams`'s stable-core keys are required in a serialized
  config.** The three stable fields (`min_labeled_corners`, `max_components`,
  `min_corner_strength`) carry no serde defaults, so a config that omits any of
  them is rejected rather than silently defaulted — pairing with the
  `deny_unknown_fields` strictness in theme 17. The advanced knobs stay
  optional under the nested `advanced` block. If you hand-maintain chessboard
  configs, make sure all three stable keys are present.

## 10. The ML refiner is opt-in

`chess-corners/ml-refiner` used to be enabled unconditionally by every crate
here. It is now behind an `ml-refiner` cargo feature that is **off by
default**, because it links the `tract` ONNX runtime into every build — it
took the published WASM bundle from ~0.85 MB to ~10 MB (now ~1.5 MB) — and
nothing in this workspace selects `ChessRefiner::Ml`.

```toml
# Cargo.toml — turn it back on
calib-targets = { version = "0.11", features = ["ml-refiner"] }
```

The feature also exists on each individual detector crate and on the Python
bindings. While it is off, the serde value `{"refiner": "ml"}` is **rejected
at deserialization** rather than silently downgraded, so a config that asks
for the ML refiner fails loudly. `center_of_mass`, `forstner`, and
`saddle_point` are unaffected.

## 11. API revision (S1): the naming-family rename

Approved decision 1 of the pre-release public-API revision (see
`API_REVISION.md` at the repo root while it is still open). The four detector
crates now share one uniform naming family — `{X}Detector` / `{X}Params` /
`{X}Detection` — instead of the chessboard crate's generic `Detector` /
`DetectorParams` colliding in spirit with `chess_corners::Detector` /
`DetectorConfig`, and the charuco/puzzleboard/marker result types' inconsistent
`…Result` suffix. All renames are clean breaks — there are no deprecated
aliases.

### Rename table

| Crate | Old name | New name |
|---|---|---|
| `calib-targets-chessboard` | `Detector` | `ChessboardDetector` |
| `calib-targets-chessboard` | `DetectorParams` | `ChessboardParams` |
| `calib-targets-charuco` | `CharucoDetectionResult` | `CharucoDetection` |
| `calib-targets-puzzleboard` | `PuzzleBoardDetectionResult` | `PuzzleBoardDetection` |
| `calib-targets-marker` | `MarkerBoardDetectionResult` | `MarkerBoardDetection` |
| `calib-targets-marker` | `MarkerBoardParams.layout` field (serde key `"layout"`) | `MarkerBoardParams.board` field (serde key `"board"`) |
| `calib-targets-marker` | `MarkerBoardParams::new(layout)` | `MarkerBoardParams::for_board(board)` (uniform with `CharucoParams::for_board` / `PuzzleBoardParams::for_board`) |
| `calib-targets-marker` | `MarkerBoardDetector::detect_from_image_and_corners` | `MarkerBoardDetector::detect` |
| `calib-targets-marker` | `MarkerBoardDetector::detect_from_image_and_corners_with_diagnostics` | `MarkerBoardDetector::detect_with_diagnostics` |

`MarkerBoardDetector::detect_from_corners` and
`detect_from_corners_with_diagnostics` (the corners-only secondary path, with
no image to score circles against) are **removed** in the diagnostics-gating
step below (§14) — they had zero consumers workspace-wide and duplicated
`calib-targets-chessboard`'s image-free detector for that case.

```rust
// before
use calib_targets_chessboard::{ChessCorner, Detector, DetectorParams};
let det = Detector::new(DetectorParams::default())?;

// after
use calib_targets_chessboard::{ChessCorner, ChessboardDetector, ChessboardParams};
let det = ChessboardDetector::new(ChessboardParams::default())?;
```

```rust
// before
let params = MarkerBoardParams::new(layout);
let result = detector.detect_from_image_and_corners(&view, &corners);

// after
let params = MarkerBoardParams::for_board(board);
let result = detector.detect(&view, &corners);
```

```jsonc
// marker-board config: "layout" → "board" (serde key, no legacy alias)
// before: { "marker": { "layout": { "rows": 22, "cols": 22, ... }, ... } }
// after:  { "marker": { "board":  { "rows": 22, "cols": 22, ... }, ... } }
```

The WASM TypeScript result interfaces are now uniformly `{X}Detection`: the
last stale one, `ChessboardDetectionResult`, is renamed to
`ChessboardDetection` to match (the ChArUco / marker / PuzzleBoard interfaces
already used the short name), and the `MarkerBoardParams` interface's
`layout` field becomes `board` with a `MarkerBoardSpec` shape. Python's result
classes (`ChessboardDetectionResult`, `CharucoDetectionResult`,
`MarkerBoardDetectionResult`, `PuzzleBoardDetectionResult`) are independent of
the Rust type names and keep their existing spellings in this release; only
Python's `MarkerBoardParams.layout` attribute follows the wire rename to
`board`.

## 12. API revision (S2): dead-item removal

Approved decision 2 of the pre-release public-API revision (see
`API_REVISION.md` at the repo root while it is still open). Every item below
had zero real consumers (verified by a workspace-wide consumer sweep — see
`API_REVISION.md`'s "Consumer evidence" sections) and carried no behaviour
that a removal could silently change: a dead C-ABI-mirrored params field that
was never read, five internal crate-bridge functions with no callers outside
their own tests, a logger-init pair that every consumer can replace with a
one-line local `env_logger` / `tracing_subscriber` call, a redundant facade
convenience wrapper, a preset that was already identical to `default()`, and
an internal orchestrator function that leaked to `pub` with no external
caller.

### Removed items

| Item | Crate | Replacement |
|---|---|---|
| `PuzzleBoardParams.corner_redetect_params` | `calib-targets-puzzleboard` | none — the field was never read by the detector; delete the assignment |
| `ct_puzzleboard_params_t.corner_redetect_params` (C ABI) | `calib-targets-ffi` | none — mirrored the dead Rust field |
| `homography_to_next` / `homography_from_next` | `calib-targets-core` | none — internal `nalgebra::Projective2` bridge, zero consumers |
| `axis_estimate_from_next` | `calib-targets-core` | none — internal bridge, zero consumers (`axis_estimate_to_next` is retained; it is used by the chessboard pipeline and the bench harness) |
| `grid_transform_to_next` / `grid_transform_from_next` | `calib-targets-core` | none — internal bridge, zero consumers |
| `init_with_level` | `calib-targets-core` | initialize your own logger in your application, e.g. `env_logger::init()` |
| `init_tracing` | `calib-targets-core` | initialize your own `tracing` subscriber in your application, e.g. `tracing_subscriber::fmt().with_env_filter(EnvFilter::from_default_env()).init()` |
| `calib_targets::detect::default_puzzleboard_params` | `calib-targets` (facade) | `PuzzleBoardParams::for_board(PuzzleBoardSpec::new(rows, cols, 1.0)?)` |
| `ChessboardParams::topological()` | `calib-targets-chessboard` | `ChessboardParams::default()` (the two were already identical — `Topological` is the sole grid builder as of theme 8) |
| `calib_targets_chessboard::detect_all_topological` (public re-export) | `calib-targets-chessboard` | `ChessboardDetector::detect_all` (the production entry point; the internal function itself is unchanged, just no longer `pub`) |

`calib-targets-core`'s `logger` module is deleted outright (it had no
remaining logic once both functions left), and the crate drops its now-unused
`log`, `tracing`, and `tracing-subscriber` dependencies; the `tracing` cargo
feature itself is unchanged — it still forwards to
`projective-grid/tracing`.

### Rust

```rust
// before
use calib_targets_core::init_tracing;
init_tracing(false);

// after — inline in your own binary/example
use tracing_subscriber::EnvFilter;
let filter = EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"));
let _ = tracing_subscriber::fmt().with_env_filter(filter).try_init();
```

```rust
// before
let params = calib_targets::detect::default_puzzleboard_params(rows, cols)?;

// after
let spec = calib_targets::puzzleboard::PuzzleBoardSpec::new(rows, cols, 1.0)?;
let params = calib_targets::puzzleboard::PuzzleBoardParams::for_board(spec);
```

Python and WASM are unaffected: the Python `default_puzzleboard_params(rows,
cols)` function and the WASM `default_puzzleboard_params` export keep their
existing behaviour (the Python binding now builds the params directly
instead of calling through the removed facade helper; the WASM binding
already built them directly).

## 13. API revision (S3): tuning knobs moved to `advanced`

Approved decision of the pre-release public-API revision. This brings the
ChArUco and PuzzleBoard configs onto the same discipline the chessboard config
already uses: a small stable, semver-covered core plus an opt-in, explicitly
**unstable** `advanced` tier that is not covered by semver. Tuning-grade knobs
that had leaked onto the stable core move into the advanced tier.

**Detection output is byte-identical at default params** — the moved knobs keep
their previous default values, and an unset `advanced` (`None`) behaves exactly
like the advanced struct's `Default`.

### ChArUco — `CharucoParams`

- `advanced` changes from a plain `CharucoAdvancedTuning` to
  `Option<Box<CharucoAdvancedTuning>>` (`None` = defaults), set via the new
  `CharucoParams::with_advanced(...)` builder and read via
  `CharucoParams::effective_tuning() -> Cow<'_, CharucoAdvancedTuning>`.
- Three knobs move off the stable core into `CharucoAdvancedTuning`:
  `grid_smoothness_threshold_rel` (0.05), `corner_validation_threshold_rel`
  (0.08), `min_secondary_marker_inliers` (1).
- `corner_redetect_params` is now `pub(crate)` — it leaked the upstream
  `chess_corners` parameter type and was `#[serde(skip)]`, so JSON / binding
  consumers could never set it. Corner refit behaviour is unchanged.

```rust
// before
let mut params = CharucoParams::for_board(&board);
params.min_secondary_marker_inliers = 2;
params.corner_validation_threshold_rel = 0.1;
params.advanced.bit_likelihood_slope = 40.0;

// after — build the advanced tuning and attach it
let mut advanced = params.effective_tuning().into_owned();
advanced.min_secondary_marker_inliers = 2;
advanced.corner_validation_threshold_rel = 0.1;
advanced.bit_likelihood_slope = 40.0;
let params = params.with_advanced(advanced);
```

```jsonc
// JSON config — before (flat top-level keys)
{ "board": { … }, "min_secondary_marker_inliers": 2,
  "grid_smoothness_threshold_rel": 0.05, "corner_validation_threshold_rel": 0.1 }

// after (nested under "advanced")
{ "board": { … },
  "advanced": { "min_secondary_marker_inliers": 2,
                "grid_smoothness_threshold_rel": 0.05,
                "corner_validation_threshold_rel": 0.1 } }
```

### PuzzleBoard — `PuzzleBoardDecodeConfig`

- The soft-scorer knobs move into a new `PuzzleBoardAdvancedTuning`:
  `bit_likelihood_slope` (12.0), `per_bit_floor` (−6.0),
  `alignment_min_margin` (0.02). `PuzzleBoardDecodeConfig` gains
  `advanced: Option<Box<PuzzleBoardAdvancedTuning>>` (the knobs semantically
  belong to the decode-scoring stage), plus the `with_advanced(...)` /
  `effective_tuning()` pair.
- The 5-argument positional constructor
  `PuzzleBoardDecodeConfig::new(min_window, min_bit_confidence,
  max_bit_error_rate, search_all_components, sample_radius_rel)` is removed.
  Build with `Default` + struct-update / field assignment.

```rust
// before
let mut cfg = PuzzleBoardDecodeConfig::new(7, 0.15, 0.3, true, 1.0 / 6.0);
cfg.bit_likelihood_slope = 15.0;

// after
let mut cfg = PuzzleBoardDecodeConfig { min_window: 7, ..Default::default() };
cfg = cfg.with_advanced(PuzzleBoardAdvancedTuning { bit_likelihood_slope: 15.0,

```

```jsonc
// JSON config — before (flat under "decode")
{ "decode": { "bit_likelihood_slope": 15.0, "per_bit_floor": -6.0,

```

Both advanced structs serialize the nested `"advanced"` object only when set;
a default config omits it entirely and carries only the stable keys.

## 14. API revision (S4): diagnostics are feature-gated uniformly

Approved decision of the pre-release public-API revision (see
`API_REVISION.md` at the repo root while it is still open). Before this step
two of the four detectors (`calib-targets-charuco`, `calib-targets-puzzleboard`)
already gated their diagnostics behind an opt-in `diagnostics` cargo feature;
`calib-targets-marker`'s diagnostics were always compiled in, and
`calib-targets-chessboard`'s `trace_topological` was an ungated function on the
always-on surface. All four now follow the same contract: the `diagnostics`
module, its type re-export, and `detect_with_diagnostics` (or
`trace_topological` for the chessboard) reach the public surface only with the
feature enabled.

- **`calib-targets-marker` gains a `diagnostics` cargo feature** (default
  off). Without it, `MarkerBoardDiagnostics` and
  `MarkerBoardDetector::detect_with_diagnostics` are absent from the public
  API; the detector still computes the diagnostics evidence internally
  (circle candidates/matches, per-corner provenance) — the feature only
  controls whether it reaches the caller.
- **`calib-targets-chessboard`'s `trace_topological` moves behind the
  existing `diagnostics` feature** (previously declared but gating no code).
  Without the feature, `trace_topological` is absent from the public API.
- **`MarkerBoardDetector::detect_from_corners` and
  `detect_from_corners_with_diagnostics` are removed.** Both had zero
  consumers workspace-wide (verified by a workspace-wide sweep) and
  duplicated `calib-targets-chessboard`'s image-free detector for the
  corners-only case. If you were calling the corners-only path, detect
  directly against `calib-targets-chessboard`:

  ```rust
  // before
  let result = marker_detector.detect_from_corners(&corners);

  // after — use the chessboard detector directly for the image-free case
  let chess = chess_detector.detect(&corners);
  ```

- The facade `calib-targets/diagnostics` feature now forwards to all **four**
  detector crates (`calib-targets-chessboard`, `-charuco`, `-puzzleboard`,
  `-marker`).

```toml
# Cargo.toml — turn the marker/chessboard diagnostics surface back on
calib-targets-marker = { version = "0.11", features = ["diagnostics"] }
calib-targets-chessboard = { version = "0.11", features = ["diagnostics"] }
# or, through the facade:
calib-targets = { version = "0.11", features = ["diagnostics"] }
```

Python, WASM, and FFI bindings already enable the facade `diagnostics`
feature (and, for WASM, each detector crate's `diagnostics` feature directly)
unconditionally, so this step is manifest-only for them — no binding code
changes.

## 16. API revision (S6): unified multi-config sweep semantics

Approved decision of the pre-release public-API revision (see `API_REVISION.md`
at the repo root while it is still open). The three target-detector sweep
helpers converge on one contract instead of three divergent ones:

| Helper | Before | After |
|---|---|---|
| `detect_charuco_best` | one corner pass for the whole sweep; configs that disagreed on `chess` returned `DetectError::InconsistentChessConfig` | honours each config's `chess`; corner pass deduplicated across configs that share one |
| `detect_marker_board_best` | one corner pass for the whole sweep; a `chess` disagreement silently collapsed the sweep to `None` | honours each config's `chess`; corner pass deduplicated across configs that share one |
| `detect_puzzleboard_best` | honoured each config's `chess`, but by running a *full* detection (corner pass included) per config | honours each config's `chess`; corner pass deduplicated across configs that share one |

The `DetectError::InconsistentChessConfig` variant is **removed** — it existed
only to reject sweeps the helpers can now serve, so it leaked the "one corner
pass" implementation detail into the user-facing contract. (Because 0.11.0 has
never shipped, the variant was never a released API; there is no two-step
migration.) Corner detection now runs once per *distinct* `chess` front-end and
is reused across every config that requests it, so mixing front-ends in one
sweep just works (e.g. a single-scale config alongside an
`UpscaleConfig::Fixed(2)` config, as `PuzzleBoardParams::sweep_for_board`
produces), and a same-`chess` sweep still pays for exactly one corner pass.

Scoring and tie-breaking are unchanged: ChArUco ranks by markers-then-corners
with the first best result winning ties; marker-board ranks by most corners with
the last maximum winning ties; PuzzleBoard ranks by labelled-corners-then-mean-
confidence with the first best result winning ties.

`detect_chessboard_best` is unchanged — it takes one explicit `chess_cfg`
argument for the whole sweep and never carried the constraint.

```rust
// before — a charuco sweep mixing corner front-ends was rejected
let configs = vec![base, base_upscaled]; // differ only on `chess`
let result = detect_charuco_best(&img, &configs);
// => Err(DetectError::InconsistentChessConfig)

// after — the same sweep runs; each config uses its own front-end, and the
// shared front-ends (if any) still cost only one corner pass
let result = detect_charuco_best(&img, &configs)?; // Ok(best detection)
```

## 17. API revision (S7 + S8): convention fixes and the chess-config rule

Approved decisions of the pre-release public-API revision (see `API_REVISION.md`
at the repo root while it is still open). S7 tightens a handful of type-level
conventions; S8 is documentation only (no behaviour change).

### `#[non_exhaustive]` + named constructors

Five public types that were still literal-constructible gain `#[non_exhaustive]`
plus a named constructor, so a future field addition is no longer a breaking
change for downstream code:

| Type | Crate | Constructor |
|---|---|---|
| `MarkerDetection` | `calib-targets-aruco` | `new(id, gc, rotation, hamming, code, corners_rect)` + `with_scores` / `with_inverted` / `with_corners_img` |
| `MarkerCell` | `calib-targets-aruco` | `new(gc, corners_img)` |
| `CellSamples` | `calib-targets-aruco` | `new(cells_per_side, bits_per_side, border_bits, mean_grid, otsu_threshold, border_black_fraction)` |
| `RectifiedView` | `calib-targets-core` | `new(rect, px_per_square, cells_x, cells_y, rect_to_img)` |
| `ChessCorner` | `calib-targets-chessboard` | `new(position, axes, strength)` (the position-only `from_position` fixture helper stays) |

If you built any of these with a struct literal, switch to the constructor:

```rust
// before
let corner = ChessCorner { position, axes, strength };
// after
let corner = ChessCorner::new(position, axes, strength);
```

`MarkerDetection` splits into a `new` for the marker identity and rectified-frame
geometry plus `with_*` builders for the decode-quality and image-frame fields —
the geometry a consumer relies on (`corners_rect`) is required, the recoverable
metadata (`score`/`border_score`, `inverted`, `corners_img`) defaults:

```rust
// before
let det = MarkerDetection { id, gc, rotation, hamming, score, border_score,
    code, inverted, corners_rect, corners_img: None };
// after
let det = MarkerDetection::new(id, gc, rotation, hamming, code, corners_rect)
    .with_scores(score, border_score)
    .with_inverted(inverted);
```

### Result types are `Serialize + Deserialize` everywhere

Previously only the marker-board result types round-tripped through serde; the
other three families were serialize-only. `ChessboardDetection` /
`ChessboardCorner`, `CharucoDetection` / `CharucoCorner`, and
`PuzzleBoardDetection` / `PuzzleBoardCorner` / `PuzzleBoardDecodeInfo` now derive
`Deserialize` too, so a saved detection JSON can be read back into its typed
struct. This is purely additive.

### `CharucoDetectError::UnsupportedAlgorithm` is removed

The variant existed to surface a chessboard-configuration rejection, but the
chessboard validator accepts every configuration the public surface can express,
so it was unreachable. It is removed. Because ChArUco error variants stringify at
every binding boundary (Python message, WASM `Error`, and the FFI generic
detection-failure status), no binding surface or C header changed.

### `deny_unknown_fields` is enforced on params/config structs

`ChessboardParams` already rejected unknown keys under
`#[serde(deny_unknown_fields)]`. That strictness is now uniform across the params
families: `CharucoParams`, `PuzzleBoardParams`, `PuzzleBoardDecodeConfig`,
`MarkerBoardParams`, the two circle-config structs (`CircleScoreParams`,
`CircleMatchParams`), and every `advanced`-tuning block reject unknown keys too.

**Migration consequence for config files.** A JSON config with a stray or
misspelled key that used to be silently ignored now fails to deserialize with a
clear `unknown field` error. This is the intended behaviour — it catches config
typos at load time instead of leaving a tuning change silently un-applied — but
if you hand-maintain config files, drop keys that are not real fields. The
first-party producers (the Python `calib_targets` config layer, the Studio
backend, and the checked-in `testdata/*.json` fixtures that flow through the
public params) already emit only valid keys and are unaffected.

> Not covered here: the aruco `ScanDecodeConfig` / `ArucoScanConfig` retain their
> current tolerance (`ScanDecodeConfig` uses a container-level `#[serde(default)]`
> and `ArucoScanConfig` still accepts the legacy `max_hamming` key), because they
> are shared aruco surfaces rather than one of the four detector-crate params
> families.

### S8: where the corner front-end config lives

Documentation only. The rule was already true; it is now stated where a user
meets it (the facade `detect` module docs, `default_chess_config`, and each
compound-target `chess` field): for **ChArUco / PuzzleBoard / marker** boards set
the corner front-end on `params.chess`; for a **plain chessboard** pass the
corner config alongside `ChessboardParams` at the facade —
`detect_chessboard(img, &chess_cfg, &params)`. A plain chessboard detector is a
reusable corner-cloud consumer, so the facade keeps its corner config separable;
a compound target always owns its full image pipeline, so its params bundle the
front-end.

## 18. Ergonomics fixes

A final consumer-ergonomics pass over the facade. Four changes; the first is a
breaking control-flow change, the rest are mechanical.

### 18a. Every facade `detect_*` entry point returns `Result` (Breaking)

The chessboard and marker-board facade helpers previously returned `Option`,
while the ChArUco and PuzzleBoard helpers returned `Result<_, DetectError>`.
Consuming more than one target type therefore meant switching control-flow shape
for no user-visible reason. Now **every** facade entry point returns
`Result<{X}Detection, DetectError>`, and a board that is simply not present is
reported as the new `DetectError::NoDetection { target }` variant rather than a
bare `None`:

```rust
// before — Option for chessboard / marker, Result for charuco / puzzleboard
if let Some(det) = detect::detect_chessboard(&img, &chess_cfg, &params) {
    use_it(det);
}

// after — one `?` / `match` shape for every target
let det = detect::detect_chessboard(&img, &chess_cfg, &params)?;
// or, to treat "no board" as a non-error:
match detect::detect_chessboard(&img, &chess_cfg, &params) {
    Ok(det) => use_it(det),
    Err(DetectError::NoDetection { .. }) => { /* a miss — expected, recoverable */ }
    Err(err) => return Err(err.into()),
}
```

Affected: `detect_chessboard`, `detect_chessboard_from_gray_u8`,
`detect_chessboard_best`, `detect_marker_board`,
`detect_marker_board_from_gray_u8`, `detect_marker_board_best`. The
`_from_gray_u8` pair also **flattens** — they returned `Result<Option<_>, _>`
and now return `Result<_, _>`.

Unchanged: `detect_chessboard_all` still returns `Vec` (empty = none found), and
the **crate-level** detectors (`ChessboardDetector::detect`,
`MarkerBoardDetector::detect`) still return `Option` — they are honest
corner-cloud consumers; only the facade unifies. The idiomatic bindings are
unchanged: Python still returns `None` on a miss, WASM still returns `null`, and
the C ABI still maps a miss to its existing "not found" status.

### 18b. `image` is re-exported as `calib_targets::image` (Added)

Import the `image` crate through `calib_targets::image` instead of adding a
separate `image = "0.25"` dependency: it guarantees your `GrayImage` type is the
exact one the `detect_*` helpers accept, so the two versions cannot drift and
produce a confusing "expected `GrayImage`, found `GrayImage`" error. A direct
dependency still works — the re-export is purely additive and rides the default
`image` feature.

### 18c. `for_board` takes the board by value

One consistent rule across the params families: **constructors that store the
board take it by value** (`for_board(board: BoardSpec)`), while **sweep presets
that clone into N configs take it by reference** (`sweep_for_board(&board)`).
`MarkerBoardParams::for_board` was already by value; `CharucoParams::for_board`
and `PuzzleBoardParams::for_board` change from `&spec` to `spec`:

```rust
// before
let params = CharucoParams::for_board(&board);
// after
let params = CharucoParams::for_board(board);
```

The board specs are `Copy`, so most call sites just drop the `&`.
`sweep_for_board(&board)` is unchanged.

### 18d. `AdvancedTuning` → `ChessboardAdvancedTuning`

The chessboard advanced-tuning struct is renamed to match the
`CharucoAdvancedTuning` / `PuzzleBoardAdvancedTuning` family:

```rust
// before
use calib_targets::chessboard::AdvancedTuning;
// after
use calib_targets::chessboard::ChessboardAdvancedTuning;
```

Pure rename: the serde key stays `"advanced"` and the JSON shape is unchanged, so
serialized configs need no edits.

## Every detector's params carries its own `chess` config

Not a break — a gap being closed. `CharucoParams`, `PuzzleBoardParams`, and
`MarkerBoardParams` gain a `chess: DetectorConfig` field defaulting to
`default_chess_config()`, so existing code and existing JSON keep working
unchanged.

Previously only the chessboard entry points took a `DetectorConfig`; ChArUco,
PuzzleBoard, and marker-board detection hardcoded the workspace default. That
meant the two scale stages were unreachable for three of the four targets:

- `MultiscaleConfig::Pyramid` — coarse-to-fine detection, for large frames.
- `UpscaleConfig::Fixed(2..=4)` — pre-pipeline upscale, for low-resolution
  boards whose corners land inside the ChESS ring margin (the usual cause of
  lost corners on small ChArUco crops). Output coordinates are rescaled back
  to input pixels for you, unlike upscaling the image yourself.

```rust
// after — a pyramid corner pass for a large ChArUco frame
let mut params = CharucoParams::for_board(board);
params.chess = params.chess.with_multiscale(MultiscaleConfig::pyramid_default());
let result = detect_charuco(&img, &params)?;
```

```jsonc
// the same thing in a serialized config
{ "chess": { "threshold": 15.0, "multiscale": { "pyramid": { … } }, … }, "board": { … } }
```

A note on the sweep helpers: `detect_charuco_best`,
`detect_marker_board_best`, and `detect_puzzleboard_best` all honour each
config's own `chess` front-end, so a sweep may freely mix front-ends (e.g. a
single-scale pass alongside an `UpscaleConfig::Fixed(2)` pass). Corner detection
is deduplicated across configs that request the same front-end, so a sweep whose
configs share `chess` still runs a single corner pass. See
[§16 (API revision S6)](#16-api-revision-s6-unified-multi-config-sweep-semantics)
for the full contract. (`detect_chessboard_best` is unchanged — it takes one
explicit `chess_cfg` for the whole sweep.)

In the Python and TypeScript bindings a `chess_cfg` argument passed to a
`detect_*` call now **overrides** `params.chess`; omitting it uses the params'
own value. Previously `chess_cfg` was the only channel and `params` had no say.

## C ABI: `calib-targets-ffi` → 3.0.0

Three struct-layout-breaking changes land in this cycle. Recompile C/C++
consumers against the regenerated `calib_targets_ffi.h`; `ct_version_string()`
and the CMake config-version now report `3.0.0`.

1. **`ct_chess_params_t`** collapses `threshold_rel` (`float`) +

2. **`ct_chessboard_advanced_t`** drops `max_fit_rms_ratio` along with the

3. **`ct_charuco_detector_params_t`** drops `max_hamming` (it only fed the

   `corner_validation_threshold_rel` **flat C fields are kept**; the conversion
   now routes them into the Rust `CharucoAdvancedTuning` internally, so no C
   caller change is needed for those two.

The PuzzleBoard C decode struct is unchanged: `ct_puzzleboard_decode_config_t`
keeps its `bit_likelihood_slope` / `per_bit_floor` / `alignment_min_margin`
flat C fields, which the conversion routes into the Rust
`PuzzleBoardAdvancedTuning` internally.

The **`ct_optional_bool_t` type is removed entirely** — nothing declares an
optional boolean any more. Delete any local `none_bool()`-style helper.

```c
/* before */
config.chess.params.descriptor_use_radius10 = none_bool();
config.chess.params.threshold_rel = 0.2f;
config.chess.params.threshold_abs = none_f32();

/* after */
```

## Python

- **`Threshold` and `DescriptorRing` are deleted** from
  `calib_targets.config` and from `__all__`. `ChessConfig.threshold` is a
  plain `float`, defaulting to `15.0`.
- **`DetectionParams` is new.** `nms_radius` and `min_cluster_size` move off
  `ChessStrategyConfig` onto `ChessConfig.detection`.
- Both the old threshold dict shape and the old key locations are **rejected
  with an explicit error** rather than silently defaulting, so a stale config
  fails loudly.

```python
# before
cfg = ct.ChessConfig(
    threshold=ct.Threshold.absolute(15.0),
    strategy=ct.DetectionStrategy.chess(
        ct.ChessStrategyConfig(nms_radius=2),
    ),
)

# after
cfg = ct.ChessConfig(
    threshold=15.0,
    detection=ct.DetectionParams(nms_radius=2),
)
```

Attribute paths change accordingly (the corner front-end is the top-level
`params.chess` on every detector's params — see the chess-config rule in
theme 17):

```python
# before
params.chess.strategy.chess_config.nms_radius

# after
params.chess.detection.nms_radius
```

`ChessboardParams.max_fit_rms_ratio` (one of the advanced knobs that
`to_dict` nests under `"advanced"`) is removed. Grid coordinates are
`Coord(u, v)`; the marker `CellCoords(i, j)` is retained.

The S3 tuning-knob revision follows the same flat-attribute / nested-JSON
convention the `ChessboardParams` dataclass already uses. The
`CharucoParams` fields `min_secondary_marker_inliers`,
`grid_smoothness_threshold_rel`, and `corner_validation_threshold_rel` stay as
flat dataclass attributes but now serialise under a nested `"advanced"` object
(and deserialise from there, with the old flat top-level layout still
tolerated). The `PuzzleBoardDecodeConfig` soft-scorer knobs
`bit_likelihood_slope` / `per_bit_floor` / `alignment_min_margin` likewise move
under `decode.advanced` on the wire while remaining flat attributes in Python.

## WASM / TypeScript

The published `ChessConfig` type now mirrors the real serde tree (the
declaration had drifted from the wire format in earlier releases):

```ts
interface ChessConfig {
  strategy: DetectionStrategy;      // { chess: { ring, refiner } } | { radon: … }
  threshold: number;                // was: { absolute: number } | { relative: number }
  detection: DetectionParams;       // { nms_radius, min_cluster_size } — new location
  multiscale: MultiscaleConfig;
  upscale: UpscaleConfig;

```

`Corner` drops `contrast` and `fit_rms`. `descriptorRing` / `ThresholdMode`
are removed. Grid-coordinate fields are `Coord { u, v }`.

From the S3 tuning-knob revision, the `CharucoAdvancedTuning` interface gains
`grid_smoothness_threshold_rel`, `corner_validation_threshold_rel`, and
`min_secondary_marker_inliers` (moved off the top-level `CharucoParams`), and a
new `PuzzleBoardAdvancedTuning` interface holds `bit_likelihood_slope` /
`per_bit_floor` / `alignment_min_margin` (moved off `PuzzleBoardDecodeConfig`,
now nested under `decode.advanced`). All advanced fields are optional and
omitted when unset.

> produces phantom TypeScript errors about missing exports.

---

## Verifying your migration

```bash
cargo build --workspace
cargo test --workspace
```

For the bindings:

```bash
cargo run -p calib-targets-ffi --features generate-header \
  --bin generate-ffi-header -- --check
uv run pytest crates/calib-targets-py/python_tests/
scripts/build-wasm.sh
```

If you keep a golden corner set, expect it to compare equal except where
theme 4 applies — and if a `(i, j)` label ever changes value (as opposed to a
corner appearing or disappearing), that is a bug worth reporting, not an
expected migration effect.
